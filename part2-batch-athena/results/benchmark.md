# Data scanned і час виконання: JSON проти Parquet

Усі числа — фактичні, з `QueryExecution.Statistics` Athena
(`DataScannedInBytes`, `EngineExecutionTimeInMillis`). Сирий лог — у
[benchmark.csv](benchmark.csv), кожен рядок містить `QueryExecutionId` для
звірки в консолі.

Датасет: 3 030 197 подій, 1 260 672 849 Б JSON → 1 000 000 платежів,
88 309 777 Б Parquet.

## Запити 3–5

| Запит | Джерело | Data scanned | Engine time | Виграш за обсягом |
|---|---|---:|---:|---:|
| Q3 оборот | `lab8.payments` (JSON view) | 1 260 692 423 Б (1,17 GiB) | 3 090 мс | |
| Q3 оборот | `lab8.payments_parquet` | **5 861 176 Б (5,6 MiB)** | **1 021 мс** | **215×** |
| Q4 відмови | `lab8.payments` (JSON view) | 1 260 692 423 Б | 4 271 мс | |
| Q4 відмови | `lab8.payments_parquet` | **667 929 Б (652 KiB)** | **1 017 мс** | **1 888×** |
| Q5 години | `lab8.payments` (JSON view) | 1 260 692 423 Б | 2 836 мс | |
| Q5 години | `lab8.payments_parquet` | **8 490 034 Б (8,1 MiB)** | **1 280 мс** | **148×** |

Час виконання впав лише у 2,2–4,2 раза — значно менше, ніж обсяг. Причина в
тому, що на 1,2 ГБ Athena все одно піднімає кластер і платить фіксовані
накладні: під секунду запит не опускається, скільки б даних не було.

## Column pruning і partition pruning — це різні речі

| Запит | Джерело | Data scanned | Engine | Коментар |
|---|---|---:|---:|---|
| `GROUP BY status` | JSON | 1 260 692 423 Б | 3 420 мс | читає все, щоб знайти одне поле |
| `GROUP BY status` | Parquet | **129 022 Б (126 KiB)** | 1 167 мс | **9 771×** — одна колонка з 17 |
| `count(*) WHERE dt='2026-10-05'` | JSON | 1 260 692 423 Б | 3 657 мс | **партиція не спрацювала** |
| `count(*) WHERE dt='2026-10-05'` | Parquet | **0 Б** | **413 мс** | відповідь із метаданих |
| `count(*) WHERE date_format(createdDate…)` | Parquet | 8 490 034 Б | 1 608 мс | фільтр не по партиції → full scan |

### Дві знахідки, які варто пояснити на захисті

**1. `count(*)` по Parquet сканує 0 байтів.** Кількість рядків лежить у футері
Parquet-файлу, тож Athena відповідає, не читаючи жодної колонки. На JSON це
неможливо в принципі: щоб порахувати рядки, треба їх прочитати.

**2. Partition pruning НЕ працює крізь вʼю `lab8.payments`.** Запит
`WHERE dt='2026-10-05'` просканував усі 1,17 GiB замість 1/31. Це не
помилка Athena — це наслідок того, що вʼю містить
`row_number() OVER (PARTITION BY invoiceId ...)`. Вікно розбиває дані за
`invoiceId`, а не за `dt`, тому предикат по `dt` **не можна проштовхнути під
віконну функцію**: платіж, створений 4 жовтня і завершений 5-го, має події в
обох партиціях, і щоб коректно вибрати останню, движок зобовʼязаний прочитати
обидві.

Практичний висновок: **вʼю зручна, але вона скасовує партиціонування.** Саме
тому крок 7 (CTAS у Parquet) — не косметика. Матеріалізована таблиця
партиціонована і фільтрується нормально; вʼю — ні.

## Скільки разів дешевше стало

| | JSON | Parquet |
|---|---:|---:|
| Розмір на S3 | 1 260 672 849 Б | 88 309 777 Б (**14,3×**) |
| Файлів | 31 | 213 |
| Рядків | 3 030 197 | 1 000 000 |
| Data scanned (Q4) | 1 260 692 423 Б | 667 929 Б (**1 888×**) |
| Ціна за $5/ТБ | $0,006303 | $0,0000033 |
| **Фактична ціна** | **$0,006303** | **$0,00005** |
| | | **≈126× дешевше** |

**Головне застереження.** Athena тарифікує **мінімум 10 МБ на запит**. Усі три
Parquet-запити (0,65 / 5,6 / 8,1 MiB) лежать нижче цієї межі, тож усі три
коштують однаково — $0,00005. Тому виграш у 1 888× за обсягом перетворюється
на **126× у грошах**, і це стеля для цього датасету. На 1,2 ГБ різниця
$0,0063 проти $0,00005 не має жодного практичного значення; Parquet починає
окупатися на терабайтах, де ті самі 126× — це вже $6 300 проти $50 на місяць.

## Чому Parquet від Athena більший за локальний

Локальний CTAS через DuckDB дав 79 080 980 Б у 31 файлі; Athena — 88 309 777 Б
у **213 файлах**, на 11,7 % більше. Причина — паралелізм: Athena пише по файлу
на воркер, тож на партицію виходить 6–7 файлів замість одного. Менші файли →
менші row group-и → гірший словник і гірше стиснення. Це мініатюра
**small files problem**: на 213 файлах вона коштує 11 % місця, на 200 000
файлів вона коштує більше, ніж самі дані.

## Де справді гарячі байти

Розмір по колонках (локальний Parquet, сума по всіх партиціях):

| колонка | MiB | частка |
|---|---:|---:|
| `reference` | 30,71 | **41 %** |
| `invoiceId` | 10,49 | 14 % |
| `createdDate` / `receivedAt` / `modifiedDate` | по 6,22 | 25 % |
| `customerId` | 5,43 | 7 % |
| `amount` / `finalAmount` | 3,94 / 3,82 | 10 % |
| `merchantName` / `merchantId` / `mcc` | по 0,49 | 2 % |
| `paymentMethod` / `device` | по 0,25 | 0,7 % |
| `ccy` / `failureReason` / `status` | 0,09–0,12 | 0,4 % |

41 % файлу — `reference`, випадковий UUID без дефісів. Ентропія максимальна,
тож він не стискається, і при цьому не потрібен жодному з наших запитів.
Саме тому Q4 (`status`, `paymentMethod`, `device` — разом 0,45 MiB у
локальному вимірі) сканує в 1 888 разів менше за JSON: **колонковий формат
просто не читає 41 % файлу.**
