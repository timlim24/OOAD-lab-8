## Масштаб датасету

| Показник | Значення |
|---|---|
| Усього подій | **3 030 197** |
| Унікальних `invoiceId` | **1 000 000** |
| Точних дублікатів (зайвих рядків) | **30 197** — 0,997 % |
| Подій після `DISTINCT` | 3 000 000 — рівно 3 на платіж |
| Подій, що запізнилися > 60 с | **60 824** — 2,007 % |
| Подій, що запізнилися > 1 години | **0** — 0,0000 % |
| Максимальне запізнення | 600 с = рівно 10 хвилин |
| Медіанне запізнення | 1 с |

Три відповіді на питання завдання:

1. **Унікальних `invoiceId` — 1 000 000.** Рівно мільйон, як і заявлено.
   Кожен платіж дав **рівно 3** події (`created → processing → success|failure`),
   а не «2–3»: перевірено, розподіл вироджений.
2. **Дублікатів — 30 197 (0,997 %).** Кожна продубльована подія прийшла рівно
   **двічі** — оригінал плюс один ретрай, трійок немає.
3. **Запізнілих більш ніж на годину — жодної (0 %).** Це не «запит не
   відпрацював»: генератор обмежує затримку десятьма хвилинами, і хвіст
   обривається рівно на 600 с.

### Розподіл запізнення — він бімодальний, а не плавний

| Інтервал | Подій | Частка |
|---|---:|---:|
| 0–10 с | 2 969 260 | 97,989 % |
| 10–60 с | 113 | 0,004 % |
| 60–120 с | 6 735 | 0,222 % |
| 2–5 хв | 20 137 | 0,665 % |
| 5–10 хв | 33 952 | 1,120 % |

Практичний висновок для частини 3 — скільки подій уже є на руках при різному
grace period:

| grace | покриття |
|---:|---:|
| 0 с | 32,65 % |
| 30 с | 97,99 % |
| 60 с | 97,99 % |
| **120 с** | **98,22 %** |
| 300 с | 98,88 % |
| 600 с | 100,00 % |

Дволвилинний grace із завдання ловить 98,2 % подій. Останні 1,8 % коштують ще
вісім хвилин затримки на **кожному** алерті — класичний компроміс
повнота/латентність.

### Чим партиціоновано: event time чи processing time?

```
подій, де день modifiedDate ≠ dt :  0
подій, де день receivedAt    ≠ dt : 88
```

`dt` — це **день події**, не день отримання. 88 подій сталися перед північчю,
а доїхали після. Це правильний вибір для аналітики: партиція за добу
закривається назавжди і денний звіт ніколи не змінюється заднім числом. Якби
партиціонували за `receivedAt`, учорашня партиція дописувалася б усю ніч і
кожна денна цифра була б попередньою.

## Запит 2 — дедуплікація

Вʼю [`lab8.payments`](sql/02_dedup_view.sql) повертає **1 000 000 рядків**,
`count(DISTINCT invoiceId)` — теж 1 000 000.

Що прибрав кожен крок:

```
3 030 197  сирих подій
-   30 197  ← SELECT DISTINCT       (передоставлені копії, 0,997 %)
= 3 000 000
- 2 000 000  ← row_number() = 1     (застарілі статуси created/processing)
= 1 000 000  платежів
```

Статуси після дедуплікації:

| status | платежів | % |
|---|---:|---:|
| success | 939 820 | 93,98 |
| failure | 60 180 | 6,02 |

Жоден платіж не застряг у `created`/`processing` — усі дійшли до термінального
стану. У проді так не буває, і запит 4 має другий варіант саме на цей випадок.

## Запит 7 — Parquet: наскільки дешевше

Розміри реальні (Parquet зібрано локально з тією самою схемою і SNAPPY):

| | JSON Lines | Parquet + Snappy |
|---|---:|---:|
| Байтів | 1 260 672 849 | 79 080 980 |
| Еквівалент | 1 202 MiB | **75,4 MiB** |
| Рядків | 3 030 197 | 1 000 000 |
| | | **у 15,9× менше** |

Тут складені **два різні ефекти**, і у звіті їх варто розділяти:

- **дедуплікація**: 3 030 197 → 1 000 000 рядків, це 3,03×. Її дав би й CTAS
  у JSON;
- **кодування**: решта ~5,2× — колонкове зберігання прибирає повторення імен
  ключів у кожному рядку, dictionary-кодує 10 назв мерчантів / 4 методи /
  3 пристрої, бітпакує цілі.

Розмір по колонках показує, куди пішли байти:

| колонка | MiB | частка |
|---|---:|---:|
| reference | 30,71 | 41 % |
| invoiceId | 10,49 | 14 % |
| createdDate | 6,22 | 8 % |
| receivedAt | 6,22 | 8 % |
| modifiedDate | 6,22 | 8 % |
| customerId | 5,43 | 7 % |
| amount | 3,94 | 5 % |
| finalAmount | 3,82 | 5 % |
| merchantName / merchantId / mcc | по 0,49 | 2 % |
| paymentMethod / device | по 0,25 | 0,7 % |
| ccy / failureReason / status | 0,09–0,12 | 0,4 % |

41 % файлу — це `reference`, випадковий UUID без дефісів. Він не стискається
(ентропія максимальна) і в жодному з наших запитів не потрібен. **Саме тому
колонковий формат виграє:** Athena його просто не читає.

### Data scanned і час виконання

| Запит | JSON | Parquet | у скільки разів менше |
|---|---:|---:|---:|
| Q3 оборот | ~1 202 MiB | **5,01 MiB** | ~240× |
| Q4 відмови | ~1 202 MiB | **0,58 MiB** | ~2 070× |
| Q5 години | ~1 202 MiB | **6,22 MiB** | ~193× |
| `GROUP BY status` | ~1 202 MiB | **0,09 MiB** | ~13 000× |

Parquet-цифри — це сума стиснутих розмірів колонок, яких торкається запит;
Athena рахує data scanned саме так.

**Але в грошах виграш менший, і це важливо сказати вголос.** Athena тарифікує
**мінімум 10 МБ на запит**:

| | data scanned | білиться як | ціна при $5/TB |
|---|---:|---:|---:|
| JSON | 1 202 MiB | 1 202 MiB | **$0,0063** |
| Parquet | 0,58–6,22 MiB | 10 MiB | **$0,00005** |

Тобто реальна економія впирається в стелю ≈ **126×**, а не 2 070×. На місячному
масштабі з сотнею дашбордних запитів це $0,63 проти $0,005 — різниця
непринципова. Парке починає окупатися не на 1,2 ГБ, а на терабайтах, і там
126× — це вже $6 300 проти $50 на місяць.

Є й другий, часто більший виграш, якого немає в таблиці: `lab8.payments` — це
**вʼю**, тобто `DISTINCT *` + `row_number()` по 3 мільйонах рядків
**перераховуються на кожному зверненні**. `payments_parquet` — матеріалізований
результат тієї ж роботи. Різниця в часі виконання між ними більша, ніж різниця
в data scanned, бо шафл для віконної функції — найдорожча частина запиту.

## Шлях Б — Glue Crawler

```bash
./setup.sh crawler
aws glue get-crawler --name ooad-lab8-payments-crawler --query 'Crawler.State' --output text
aws glue get-table --database-name lab8_crawled --name payments \

```

### 1. Які типи він обрав для `amount`, `ccy` і дат? Чи розпізнав `dt` як партицію?

| поле | наша схема | що зазвичай ставить crawler |
|---|---|---|
| `amount`, `finalAmount` | `bigint` | `int` — значення влазять у 32 біти, і JSON-класифікатор Glue бере найвужчий тип, що підійшов під **семпл** |
| `ccy`, `mcc` | `int` | `int` |
| `createdDate`, `modifiedDate`, `receivedAt` | `string` | `string` — crawler **не** парсить ISO-8601 у `timestamp` |
| `dt` | партиція `string` | **так**, партиція `string` — розпізнається за Hive-шаблоном `dt=` у шляху |
| `failureReason` | `string` | `string`, якщо потрапив у семпл |

Головний ризик тут — `int` для `amount`. Поки максимум ~100 000 копійок, усе
добре. Перший платіж на понад 21 474 836,47 ₴ переповнює int32, і crawler при
наступному запуску **мовчки змінить тип на `bigint`** — а все, що читало цю
таблицю з очікуванням int, зламається або почне віддавати NULL. Ми поставили
`bigint` одразу, бо знаємо предметну область: гроші в мінорних одиницях завжди
bigint.

Другий ризик — дати. Для crawler-а це просто рядки, тож будь-який запит із
часом усе одно треба обгортати в `from_iso8601_timestamp()`. Ніякої переваги
над ручною схемою тут немає — тільки ілюзія, що «схема сама зʼявилася».

> Заповнити фактичним виводом `get-table` у
> [results/crawler_schema.md](results/crawler_schema.md).

### 2. Що сталося з `failureReason`, якого немає в більшості подій?

Він **є** у схемі як `string`, і це важливо зрозуміти правильно.

У JSON Lines відсутній ключ — це не помилка і не NULL у файлі, його просто
немає в обʼєкті. JSON SerDe при читанні повертає для такої колонки `NULL`.
Crawler сканує вибірку файлів, зустрічає хоч один `failure`-рядок із цим
ключем — і додає колонку в схему. Оскільки в нас 6 % подій це failure
(60 180 платежів), ймовірність не натрапити на жоден — нульова.

**Але це щастя, а не гарантія.** Якби поле зустрічалося в 0,01 % подій і лише в
одному файлі з 31, crawler міг би його не побачити взагалі — він читає семпл,
а не все. Тоді колонка просто **зникає зі схеми**, запити по ній падають з
`Column 'failurereason' cannot be resolved`, і причину шукають годину. Це
фундаментальне обмеження інференсу: **він бачить тільки те, що потрапило у
вибірку.**

Інверсія тієї ж проблеми гірша: якщо в одному файлі поле приходить числом, а в
іншому рядком, crawler або зводить тип до `string`, або створює **дві різні
таблиці** для одного префікса, бо вирішить, що це різні схеми.

### 3. Яка схема зручніша для запитів і чому ручні схеми все одно поширені?

**Для запитів — вони майже однакові**, і це чесна відповідь. Crawler віддає
робочу таблицю, по ній можна писати SQL. Ручна краща рівно в одному місці —
`bigint` замість `int` — і це не «зручність», а коректність на даних, яких ще
немає.

Чому ручні схеми все одно пишуть:

1. **Стабільність.** Crawler за розкладом може змінити тип колонки, і запит,
   який працював учора, сьогодні падає. Ручна схема в git не змінюється сама.
2. **Схема — це контракт, і він має проходити код-рев'ю.** DDL у репозиторії
   видно в PR: «чому тут double для грошей?» — питання ставлять до релізу, а не
   після. Інферована схема зʼявляється мовчки.
3. **Ціна й латентність.** Crawler — це окремий запуск, хвилини і гроші
   ($0,44 за DPU-годину). `MSCK REPAIR TABLE` або
   `ALTER TABLE ADD PARTITION` коштують нуль. Ще краще — **partition
   projection**: ви описуєте діапазон дат у `TBLPROPERTIES`, і Athena обчислює
   партиції на льоту, взагалі без звернень до каталогу. На таблиці з тисячами
   партицій це економить десятки секунд на кожному запиті.
4. **Контроль над тим, що читається.** Ручна схема може **ігнорувати** зайві
   поля. Продюсер додав десять нових ключів — ваша таблиця їх не бачить і
   нічого не ламається.
5. **Складні випадки інференс не тягне.** Вкладені структури, масиви,
   `struct<>` з опційними полями, поля, що міняють тип між версіями API, —
   усе це crawler або розвалює, або зводить до `string`.

**Де crawler справді на місці:** розвідка незнайомих даних («що взагалі лежить
у цьому бакеті?»), дата-лейк із сотнями джерел, де вручну описати все
нереально, і першого дня проєкту, коли треба швидко подивитися на дані. Типовий
зрілий підхід — **crawler один раз для розвідки, далі згенерований DDL
вичищається руками й кладеться в репозиторій**, а crawler вимикається.

## Чому `DISTINCT` стоїть перед `row_number()` і що ламається без дедуплікації

### Чому саме в такому порядку

Поширена відповідь — «без DISTINCT вʼю поверне дублікати» — **неправильна**, і
на захисті це одразу видно. `row_number()` з `WHERE rn = 1` поверне один рядок
навіть з двох ідентичних: він пронумерує їх 1 і 2 і другий відсіється. Два
рядки повернув би `rank()` (обидва отримали б `rk = 1`), але ми користуємося
`row_number()`.

Що справді втрачається:

**1. Детермінізм.** Який із двох однакових рядків стане першим — не визначено.
Зараз вони байт-у-байт однакові, тож ніхто не помітить. Але як тільки ретрай
почне відрізнятися хоч одним полем — переserialised float, пізніший
`receivedAt`, збагачений `merchantName` — вʼю почне **віддавати різні дані на
тих самих вхідних**, а Parquet-таблиця з кроку 7 — змінюватися між запусками.
Баг — це невідтворюваний результат; дублікат — лише спосіб, яким він
проникає.

**2. `ORDER BY` з нічиєю робить вікно недетермінованим на рівні движка.**
Presto вільний взяти будь-який рядок, і вибір залежить від того, як лягли
спліти, тобто від того, скільки файлів повернув S3 цього разу. Той самий
запит, ті самі дані, інша відповідь наступного місяця.

**3. Кількість дублікатів перестає бути вимірюваною.**
`count(*) - count(DISTINCT *)` — єдине чесне визначення «скільки подій
передоставили». Якщо їх уже схлопнула інша операція, повідомити 0,997 %
неможливо. А цю метрику треба моніторити: стрибок дублікатів з 1 % до 20 % —
це зламаний ретрай на боці відправника, і дізнатися про це варто сьогодні, а не
на квартальному звіті.

**4. Це дві різні операції, що відповідають на два різні питання** — і саме
тому їх не можна зливати в одну:

| | що прибирає | природа |
|---|---|---|
| `DISTINCT` | відправник сказав це двічі | **баг транспорту**, треба алертити |
| `row_number()` | платіж пройшов через статуси | **нормальний бізнес-факт** |

Схлопнувши обидві в одну віконну функцію, ви приховуєте, що одна з них —
помилка, на яку слід реагувати.

### Що ламається без дедуплікації — з цифрами

**(а) Підрахунок платежів.** 3 030 197 замість 1 000 000 — **у 3,03× більше**.
Ця помилка абсурдна настільки, що її помітять одразу. Безпечна.

**(б) Частка відмов — ось це небезпечно.** На сирих подіях кожен платіж додає
в знаменник два не-failure рядки, і частка розмивається втричі:

| paymentMethod / device | на сирих подіях | після дедуплікації |
|---|---:|---:|
| qr / android | 2,24 % | 6,71 % |
| card / android | 2,01 % | 6,04 % |
| card / ios | 1,98 % | 5,95 % |
| apple_pay / web | 1,99 % | 5,95 % |

**2 % замість 6 %.** Число не виглядає зламаним — воно виглядає нормально.
Жоден sanity-check не спрацює, ніхто не піде розбиратися, і продуктова команда
півроку вважатиме, що з платежами все гаразд, поки реально відвалюється кожен
шістнадцятий. Абсурдна помилка безпечна; правдоподібна — ні.

**(в) Оборот — майже правильний, і тому найгірший.** `finalAmount` дорівнює
нулю в `created` і `processing`, тож історія статусів суму взагалі не роздуває.
Подвоюються лише ~1 % передоставлених `success`-подій → **завищення виручки
приблизно на 1 %**. Воно тихе, стабільне, не виходить за межі правдоподібного
і спливе аж на реконсиляції з банком.

**(г) Унікальні клієнти — не зачеплені взагалі.** `COUNT(DISTINCT customerId)`
ідемпотентний і дає однакову відповідь до і після дедуплікації. Саме тому
«у мене запит відпрацював нормально» **не є доказом**, що пайплайн
дедуплікований.

Загальне правило, яке варто сформулювати на захисті:

> Дедуплікація ламає не всі агрегати, а тільки ті, що **рахують події**.
> `COUNT`, `AVG`, частки — ламаються. `COUNT DISTINCT`, `MIN`, `MAX` —
> ні. `SUM` — залежить від того, чи нульове поле в неостаточних станах.
> Тому «працює» — не критерій, і дедуплікувати треба **до** агрегації
> завжди, а не там, де помітили розбіжність.
