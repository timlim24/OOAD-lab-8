# Частина 3 — Стрімінг локально: Redpanda + Python

## Запуск

```bash
# 0. одноразово: доступ до docker без sudo
sudo usermod -aG docker $USER && newgrp docker

make venv          # .venv + kafka-python-ng
make data          # качає dt=2026-10-01 з публічного бакета
make up            # redpanda + console, чекає на healthy
make topic         # топік payments, 3 партиції
make produce       # реплей дня, ~20 платежів/с
make consume       # у другому терміналі
```

Console — http://localhost:8080, брокер — `localhost:19092`.

| Файл | Що це |
|---|---|
| [docker-compose.yml](docker-compose.yml) | Redpanda v25.2.5 + Console v3.4.0 |
| [producer.py](producer.py) | реплей дня в топік у порядку `receivedAt` |
| [consumer.py](consumer.py) | дедуплікація + віконна частка відмов + алерти |
| [simulate.py](simulate.py) | та сама логіка консюмера **без брокера** — для перевірки |
| [Makefile](Makefile) | `make help` |

### `simulate.py` — навіщо

Імпортує той самий клас `WindowedFailureRate` із [consumer.py](consumer.py) і
згодовує йому файл у порядку `receivedAt` — тобто рівно те, що надіслав би
продюсер. Дає змогу перевірити логіку вікон до того, як зʼявиться Docker, і —
головне — **отримати очікувані числа для кожного експерименту**, щоб відрізнити
реальну різницю від власної помилки.

Усі цифри нижче отримані саме ним на `dt=2026-10-01` і **повністю
детерміновані**: і вибір «зламаних» платежів, і причина відмови виводяться з
хешу `invoiceId`, без жодного RNG. Про те, чому це принципово, — нижче,
у розділі про експеримент 3.

## Як воно влаштоване

### Продюсер: стискання часу

День 2026-10-01 — це 101 084 події для 33 361 платежу, розтягнутих на 24 години.
Щоб віддавати 20 платежів/с, увесь день треба стиснути в
`33 361 / 20 ≈ 1 668 с ≈ 28 хвилин`, тобто **speed factor ≈ 52×**: одна секунда
реального часу = 52 секунди часу подій.

Важливо, що масштабується **весь** таймлайн, разом із запізненнями. Подія, яка
в датасеті прийшла на 10 хвилин пізніше, прийде на `600/52 ≈ 11,5` реальних
секунд пізніше. Для консюмера це прозоро, бо його вікна живуть в **event
time**, а не в реальному: він бачить ті самі 60-секундні вікна й ті самі
10-хвилинні запізнення, просто все відбувається швидше.

Сон рахується від `wall_start` щоразу заново, а не накопиченням `sleep()`:
інакше кожна повільна відправка зсувала б увесь подальший реплей, і до кінця
дня дрейф набіг би на хвилини.

### Чому `key=invoiceId`

`kafka-python` хешує ключ **murmur2** — тією ж функцією, що й Java-клієнт. Усі
три події одного платежу дають той самий хеш → ту саму партицію → **той самий
порядок**. Без ключа повідомлення розкладались би round-robin і `success` міг
би обігнати `processing` у різних партиціях.

Порядок Kafka гарантує **тільки в межах партиції**. Ключ — це єдиний спосіб
перетворити цю гарантію на щось корисне.

### Консюмер: watermark і grace

```
watermark = max(modifiedDate), який ми бачили
вікно [T, T+60) закривається, коли watermark >= T + 60 + grace
подія, чиє вікно вже закрите → rejected as late
```

Watermark монотонний за побудовою (`max()` не зменшується). Це той самий підхід,
що у Flink `BoundedOutOfOrderness`. Чого він не вміє — **рухатися, коли стрім
мовчить**, тому в консюмері є ще й idle-flush: якщо 15 секунд нічого не
прийшло, відкриті вікна закриваються примусово. Без цього останні вікна
скінченного реплею не закрилися б ніколи, і консюмер виглядав би зависнутим.

### Знаменник — тільки термінальні події

`created` і `processing` — це не «не відмова», це «відповіді ще немає». Якщо
покласти їх у знаменник, отримаємо рівно ту помилку, яку виміряно в
[частині 2](../part2-batch-athena/README.md): **6 % перетворюється на 2 %**.
Тому консюмер рахує частку по `success` + `failure`, а решту лише лічить
окремо (`non-terminal (skipped)`).

### Ключ дедуплікації

`(invoiceId, status, modifiedDate)` — **бізнес-ідентичність** події, а не хеш
байтів. Та сама (платіж, статус, момент) — це та сама подія, навіть якщо
ретрай переserialised JSON з іншим порядком ключів чи пробілами. Хеш байтів
такий ретрай пропустив би.

## Базовий прогін

Продюсер відпрацював повний день у топік `payments` рівно за планом:

```
sent        : 101,084 events for 33,361 payments
delivered   : 101,084
wall time   : 1668.1s (20.0 payments/s)
```

Рівно **20,0 платежів/с** — цільовий темп із завдання. Темп нерівний: на
початку реплею (нічні години) ~13/с, під кінець (вечірній пік) ~21/с, бо
реплей зберігає форму добового профілю.

Консюмер на брокері (3 партиції) і офлайн-еталон на тому самому файлі:

| | `simulate.py` (без брокера) | консюмер на Redpanda |
|---|---:|---:|
| events received | 101 084 | **101 084** |
| duplicates dropped | 1 001 (0,990 %) | **1 001 (0,990 %)** |
| rejected as LATE | 1 680 (1,662 %) | 140 (0,138 %) |
| counted into windows | 32 798 | 33 314 |
| windows closed | 1 433 | **1 433** |
| alerts fired | 51 | 55 |
| dedup set, пік | 100 083 | **100 083** |

Кількість подій, дублікатів, вікон і розмір множини дедупу збігаються **точно**.
Різниця лише в запізнілих — і вона пояснюється нижче, в
[експерименті 4](#експеримент-4--grace--0): poll-батч працює як додатковий
grace.

Звірка з батчем: 0,990 % дублікатів проти 0,997 % з Athena по всьому місяцю.
1 433 вікна замість 1 440 — сім хвилин доби не мали жодної термінальної події
(глибока ніч).

## Експеримент 1 — зупинити консюмер на хвилину

```bash
make produce            # хай крутиться
make consume            # Ctrl-C через 2 хвилини
sleep 60
make consume            # запустити знову
```

**Що відбувається.** Нічого не губиться. Kafka — це **лог**, а не черга:
повідомлення не зникає після читання, воно лежить у партиції до закінчення
retention. Консюмер зберігає в брокері лише **offset** — номер позиції у
кожній партиції. При рестарті та сама `group.id` отримує свої офсети назад і
читає далі з того самого місця.

У консюмері навмисно `enable_auto_commit=False` і ручний `commit()` раз на
5 секунд **після** того, як події згорнуті у вікна. З автокомітом клієнт міг би
закомітити офсет повідомлення, яке прочитав, але ще не обробив, — і падіння між
цими двома моментами втратило б дані. Ручний коміт дає **at-least-once**: після
рестарту до 5 секунд подій прийдуть удруге, і їх прибере та сама дедуплікація,
що й ретраї вебхука. Те саме колесо, два різні джерела дублікатів.

**Що подивитися в Console:** вкладка *Consumer Groups* → `failure-rate-monitor`.
Поки консюмер стоїть, **Lag** росте — це буквально кількість повідомлень, які
його чекають. Після рестарту lag за кілька секунд падає до нуля: консюмер
«доганяє» вичитуванням з диска швидше, ніж продюсер пише.

**На що звернути увагу у виводі.** Стан вікон у памʼяті при зупинці **втрачається**
— відновлюються тільки офсети. Якщо вікно було наполовину зібране, після
рестарту воно перечитається з офсету й збереться наново; але якщо коміт устиг
пройти за середину вікна, частина подій уже не перечитається і вікно
закриється неповним. Це головна причина, чому Flink має **чекпоінти стану**, а
не лише офсети: у проді зберігати треба і те, і те, атомарно.

> Повний вивід і таблиця lag: [results/exp1_restart.md](results/exp1_restart.md)

## Експеримент 2 — два консюмери в одній групі

```bash
make consume            # термінал 1
make consume            # термінал 2, та сама group.id
```

**Що відбувається.** Топік має 3 партиції, консюмерів стає 2 → брокер запускає
**rebalance** і роздає партиції: одному дві, іншому одну. Обидва консюмери
друкують це самі:

```
[rebalance] revoked:  [0, 1, 2]
[rebalance] assigned: [0, 1]
```

```
[rebalance] assigned: [2]
```

**У Console:** *Consumer Groups* → `failure-rate-monitor` показує два members і
навпроти кожного — його партиції та окремий lag.

**Три речі, які варто сказати на захисті:**

1. **Партиція — це одиниця паралелізму.** Трьох консюмерів вистачить, щоб узяти
   по одній партиції. **Четвертий отримає нуль партицій і простоюватиме** —
   додавання консюмерів понад кількість партицій не прискорює нічого. Кількість
   партицій — це стеля масштабування, і міняти її потім боляче.

2. **Результати стають неповними, і це очікувано.** Кожен консюмер рахує вікна
   **тільки по своїх партиціях**, тож замість однієї частки відмов по
   `card` ви отримаєте два частинні підрахунки в двох терміналах. Щоб зводити
   глобально, потрібен або один консюмер, або другий етап агрегації (репартиція
   за `paymentMethod` — саме це робить Flink `keyBy`). Наш ключ —
   `invoiceId`, тож платіж не розʼїжджається, а `paymentMethod` розʼїжджається.

3. **Під час rebalance обробка стоїть.** З дефолтним eager-протоколом усі
   консюмери віддають усі партиції й отримують нові — «stop the world» на
   секунди. Саме тому в Kafka зʼявився cooperative rebalancing.

> Повний вивід, склад групи і випадок із 4 консюмерами: [results/exp2_two_consumers.md](results/exp2_two_consumers.md)

## Експеримент 3 — 30 % відмов

```bash
make produce ARGS="--fail-rate 0.30"
# або: python producer.py --file data/events-2026-10-01.jsonl --fail-rate 0.30
```

Продюсер детерміновано (за хешем `invoiceId`) переписує 30 % платежів у
`failure`, тримаючи запис узгодженим: `finalAmount = 0` і зʼявляється
`failureReason`.

### Підводний камінь, на який я наступив

Перша версія брала причину відмови через `rng.choice(FAILURE_REASONS)`.
Виглядає нешкідливо — і тихо ламає саме те, що лабораторна вимірює.

У датасеті ~1 % подій — **байт-у-байт однакові передоставлення**. Коли
продюсер переписує таку подію у `failure`, він робить це **двічі** — для
оригіналу й для копії. З `rng.choice` два послідовні виклики дають **різні**
причини, і дві копії перестають бути дублікатами.

Виміряно на Kinesis-прогоні через Athena:

| | дублікатів у дні |
|---|---:|
| датасет як є | **1 001** |
| після `--fail-rate 0.30` з `rng.choice` | **920** |

**Ін'єкція відмов знищила 8 % дублікатів** — тобто рівно той сигнал, який
дедуплікація має ловити. Виправлення: причина виводиться з
`sha256("reason:" + invoiceId)`, тож усі копії однієї події отримують
однакову причину й лишаються ідентичними. Після виправлення
`duplicates dropped` дорівнює 1 001 і в базовому режимі, і з `--fail-rate`.

Мораль ширша за цю лабораторну: **генератор тестових даних, який підмішує
випадковість на рівні події, непомітно змінює статистичні властивості
датасету.** Усе, що має бути однаковим у копіях, мусить виводитися з ключа,
а не з RNG.

**Результат на брокері:** алертів **55 → 326**, у 5,9 раза більше. Решта
лічильників не змінюється — 101 084 події, 1 001 дублікат, 1 433 вікна в
обох прогонах, бо ми міняємо лише значення поля `status`, а не час і не
доставку. Офлайн-еталон дає 51 → 304, той самий множник.
Деталі: [results/exp3_failures.md](results/exp3_failures.md).

### Але головне тут інше: 51 алерт на базовому прогоні — це хибні спрацювання

Справжня частка відмов у даних — **6 %**, поріг — **10 %**. Звідки 51 алерт?
З маленьких вікон. Уночі в хвилинному вікні буває 2–6 термінальних подій;
одна відмова з трьох — це 33 %, і поріг пробито шумом.

Тому в консюмері є `--min-events` (за замовчуванням 20): не алертити на комірку,
менша за N. Ось як вибір цього порога впливає на розрізнювальну здатність —
виміряно на тому самому дні:

| `--min-events` | комірок ≥ N | алертів при 6 % (хибні) | алертів при 30 % | розділення |
|---:|---:|---:|---:|---|
| 1 | 4 430 | 909 (**20,5 %**) | 3 437 (77,6 %) | погане |
| 5 | 2 498 | 662 (**26,5 %**) | 2 373 (95,0 %) | погане |
| 10 | 1 264 | 234 (**18,5 %**) | 1 224 (96,8 %) | середнє |
| **20** | **307** | **51 (16,6 %)** | **304 (99,0 %)** | **найкраще** |

Без захисту за розміром вибірки монітор кричить на кожній пʼятій нормальній
комірці — і його вимкнуть першого ж тижня. З `min-events = 20` хибні
спрацювання падають до 16,6 %, а при реальній аварії алерт ловить 99,0 %
комірок. Це і є **чутливість проти специфічності**: поріг у відсотках без
мінімального розміру вибірки — не монітор, а генератор шуму.

Дорослий варіант — не фіксований поріг, а **біноміальний тест** проти базової
частки 6 % (або контрольний ліміт `p̂ ± 3σ`), який автоматично вимагає більшої
аномалії від меншої вибірки.

## Експеримент 4 — grace = 0

```bash
python simulate.py --file data/events-2026-10-01.jsonl --grace 0
# з брокером: python consumer.py --grace 0
```

Обидва консюмери читають **той самий повний лог** із початку, різними
групами, відрізняються лише `--grace`:

| | `--grace 120` | `--grace 0` | різниця |
|---|---:|---:|---|
| events received | 101 084 | 101 084 | — |
| duplicates dropped | 1 001 (0,990 %) | 1 001 (0,990 %) | — |
| **rejected as LATE** | **140 (0,138 %)** | **227 (0,225 %)** | **+87, +62 %** |
| наскільки запізнилися (сер.) | 163 с | 190 с | +27 с |
| наскільки запізнилися (макс.) | 427 с | 537 с | +110 с |
| **counted into windows** | **33 314** | **33 284** | **−30 термінальних** |
| non-terminal (skipped) | 66 629 | 66 572 | −57 |
| windows closed | 1 433 | 1 433 | — |
| alerts fired | 55 | 53 | −2 |

Офлайн-еталон на тому самому файлі дає 1 680 → 2 532 (+50,7 %) і −299
термінальних. Напрямок і співвідношення ті самі, масштаб інший — чому саме,
нижче.

### Що саме змінилося в числах

**Відкинутих як запізнілі стало в 1,6 раза більше.** З grace = 120 вікно
чекає ще дві хвилини після свого кінця, і все, що прийшло за цей час, ще
встигає. З grace = 0 воно закривається, щойно watermark перетнув кінець.

**Вікна стали неповними: −30 термінальних подій.** Кількість вікон не
змінилася (1 433), бо вікно створює перша подія, що в нього потрапила, а не
grace.

**Максимальне зафіксоване запізнення зросло з 427 до 537 с** — при нульовому
grace консюмер «бачить» запізнення, які зі 120-секундним запасом просто не
були б запізненнями.

### Чому на брокері цифри менші, ніж в офлайн-еталоні

Це не помилка, і причину варто назвати: **розмір батчу працює як додатковий,
непроханий grace.**

- `simulate.py` викликає `close_ready()` **після кожної події** — вікна
  закриваються за найтіснішим можливим графіком.
- Консюмер викликає `close_ready()` **раз на poll-батч** (до 500 записів).
  Поки батч обробляється, watermark стоїть, і всі запізнілі події всередині
  батчу встигають у свої вікна.

Коли консюмер наздоганяє лог із диска, один батч покриває кілька хвилин часу
подій, тож фактичний grace дорівнює
`grace + (проміжок часу подій в одному батчі)`, і другий доданок переважає
перший. На живому стрімі, де батч збирається за сотні мілісекунд, цифри
зійшлися б із симуляцією.

Сама по собі корисна річ: **латентність обробки впливає на результат
віконних обчислень так само, як налаштування grace.** Два консюмери з
однаковим `--grace`, але різною швидкістю читання, дадуть різні числа.

**Частки відмов зсунулися несильно (55 проти 53 алертів) — але це властивість
датасету, а не загальне правило.** І ось найважливіше: запізнілі події
**не випадкові**. У цьому датасеті затримку отримують
2 % подій випадково, тож зсув малий. У проді запізнюється те, що проходило
складніший шлях: 3-D Secure з таймаутом, ретраї після збою банку — тобто
**непропорційно багато відмов**. Викинувши запізнілі, монітор систематично
**занижує** частку відмов саме тоді, коли вона росте, — тобто сліпне рівно в
момент аварії.

**Кількість вікон не змінилася** (1 433), бо вікно створюється першою подією, що
в нього потрапила, а не grace-ом.

### Компроміс

| grace | покриття подій | затримка алерту |
|---:|---:|---:|
| 0 с | 32,65 % на момент закриття | миттєво |
| 120 с | 98,22 % | +2 хв |
| 600 с | 100,00 % | +10 хв |

Купити останні 1,8 % повноти коштує ще **вісім хвилин** затримки на кожному
алерті. Для моніторингу платежів 2 хвилини — правильний вибір: алерт через
10 хвилин після початку аварії марний. Для нічного звіту правильний вибір —
600 секунд, бо там затримка нічого не коштує, а повнота коштує всього.

**Це і є різниця між стрімом і батчем в одному реченні:** батч бере grace, що
дорівнює добі, і тому завжди правий; стрім бере grace у дві хвилини і тому
завжди трохи неправий — але вчасно.

## Множина побачених подій росте без обмежень

Після одного дня `dedup set` містить **100 083** ключів — усі унікальні події
доби. За місяць це були б 3 000 000, а в масштабах Uklon з 580 млн GPS-пінгів
на добу — неможливо в принципі.

Кожен ключ — кортеж із трьох рядків (`invoiceId`, `status`, `modifiedDate`).
У CPython це близько 200 байтів з урахуванням накладних витрат dict → **~20 МБ
за добу**, ~600 МБ за місяць, і процес помирає по OOM. Не «колись», а за
календарем.

Що з цим роблять у проді:

| Підхід | Як | Чим платимо |
|---|---|---|
| **Redis з TTL** | `SET dedup:<key> 1 EX 900 NX` | мережевий похід на кожну подію; дедуплікація стає зовнішньою залежністю |
| **Flink keyed state + state TTL** | `StateTtlConfig`, стан у RocksDB, шардований за ключем | складність Flink; зате стан локальний і чекпоінтиться разом з офсетами |
| **Bloom filter з ротацією** | два фільтри по 15 хв, старий викидається | можливі хибнопозитивні → **втрата реальних подій** |
| **Ідемпотентний стік** | не дедуплікувати взагалі, писати `UPSERT` по ключу | потрібне сховище з первинним ключем; не працює для лічильників |

У консюмері реалізовано перший варіант у памʼяті: `--dedup-ttl N` викидає
ключі, старші за N секунд **часу подій**:

```bash
python simulate.py --file data/events-2026-10-01.jsonl --dedup-ttl 900
```

Виміряно на тому самому дні:

| | без TTL | `--dedup-ttl 900` |
|---|---:|---:|
| duplicates dropped | 1 001 (0,990 %) | **1 001 (0,990 %)** |
| dedup set, пік | 100 083 | **2 202** |
| dedup set, у кінці | 100 083 | 337 |
| памʼять (оцінка) | ~20 МБ | **~0,4 МБ** |

**Дедуплікація не втратила жодного дубліката, а памʼять впала у 45 разів.**
Це безкоштовно саме тому, що TTL (900 с) із запасом перекриває максимальне
запізнення в датасеті (600 с): ретрай фізично не може прийти пізніше, ніж
живе його ключ.

**TTL має перевищувати максимальне запізнення, проти якого ви дедуплікуєте.**
У цьому датасеті максимум — 600 с, тож 900 с дає запас. Поставите 300 — і
ретрай, що прийшов через 8 хвилин, пройде як нова подія: дедуплікація почне
мовчки пропускати дублікати саме на тих подіях, які найважче відстежити.
Перевіряється тривіально — `--dedup-ttl 300` і дивитися, чи `duplicates
dropped` досі 1 001.

> Головне, що тут варто зрозуміти: **дедуплікація без TTL — це не «поки що
> простий варіант», це витік памʼяті з відкладеним падінням.** А TTL
> перетворює абсолютну гарантію («жодного дубліката ніколи») на умовну
> («жодного дубліката в межах вікна N»), і цей компроміс треба обирати
> свідомо, а не виявляти в проді.
