# Експеримент 2 — кілька консюмерів в одній групі

Топік `payments`, **3 партиції**.

## Два консюмери, група `exp2`

Консюмер 1 стартує сам, через 25 с приєднується консюмер 2.

Вивід консюмера 1:
```
[rebalance] assigned: [0, 1, 2]     <- сам, забрав усе
[rebalance] revoked:  [0, 1, 2]     <- приєднався другий: віддав усе
[rebalance] assigned: [0, 1]        <- і отримав назад дві партиції
```

Вивід консюмера 2:
```
[rebalance] assigned: [2]
```

Стан групи в брокері під час роботи обох:

```
BALANCER   range
MEMBERS    2
TOTAL-LAG  471

TOPIC     PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG  MEMBER-ID
payments  0          11785           11942           157  kafka-python-…-37b2dd56
payments  1          11748           11933           185  kafka-python-…-37b2dd56
payments  2          11824           11953           129  kafka-python-…-938a8228
```

Партиції 0 і 1 належать одному member-id, партиція 2 — іншому. Розподіл 2+1.

Скільки кожен обробив:

| | events received | counted into windows | windows closed |
|---|---:|---:|---:|
| консюмер 1 | 37 096 | 12 158 | 753 |
| консюмер 2 | 1 494 | 492 | 40 |

Різниця величезна, бо консюмер 1 стартував першим і встиг вичитати весь лог з
початку; консюмер 2 підхопив лише свою партицію з поточної позиції групи.

## Чотири консюмери на три партиції

| | |
|---|---|
| MEMBERS | **4** |
| партиції мають власників | 3 |
| різних member-id серед власників | **3** |

Четвертий member у групі є, але **жодної партиції не має і не обробляє нічого**.

## Три висновки

**1. Партиція — одиниця паралелізму.** Трьох консюмерів досить, щоб узяти по
одній. Четвертий простоює: Kafka ніколи не віддає одну партицію двом
консюмерам однієї групи, бо це зламало б гарантію порядку. **Кількість
партицій — це стеля масштабування**, і задається вона при створенні топіка.
Збільшити можна, але це перетасує розподіл ключів по партиціях, тобто зламає
впорядкованість для вже існуючих ключів.

**2. Результати стають частинними, і це не баг.** Кожен консюмер рахує вікна
**лише по своїх партиціях**: замість однієї частки відмов по `card` ви
отримуєте два окремі підрахунки у двох терміналах. Наш ключ — `invoiceId`,
тож платіж цілком лежить в одній партиції й не розʼїжджається. А от
`paymentMethod` розʼїжджається: події з `card` рівномірно розкидані по всіх
трьох партиціях.

Щоб звести глобально, потрібен або один консюмер, або **другий етап з
репартицією за `paymentMethod`** — саме це робить `keyBy` у Flink, і саме
тому у Flink є shuffle між операторами. Наш однопроцесний консюмер цього
етапу не має, і його масштабування впирається не в партиції, а в те, що
агрегат за методом оплати глобальний.

**3. Під час rebalance обробка стоїть.** У виводі консюмера 1 видно
`revoked: [0, 1, 2]` перед `assigned: [0, 1]` — він віддав **усі** партиції,
включно з тими, які зараз же отримав назад. Це eager-протокол: «stop the
world» на секунди при кожній зміні складу групи. Саме через це в Kafka
зʼявився cooperative rebalancing, який забирає лише ті партиції, що реально
переїжджають.
